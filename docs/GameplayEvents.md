# P1.5 — Gameplay Event Inspector

Open **View → Gameplay Events**. Capture is off by default. Start Capture can be enabled before
or during Play; Stop Capture freezes the history, Pause Capture temporarily suspends observation,
and Clear History removes collected rows. These controls do not pause gameplay. Play Pause remains
an independent control. Closing the panel does not stop an explicitly enabled capture.

## Existing delivery paths observed

- `World.send_event(target, type, amount)`: one queued, addressed message, delivered to the target's
  actual `on_event`. The sender is the script owner already known by the Lua binding.
- Physics `collision`, `trigger_enter`, `trigger_exit`: existing EventBus → QueueCollision → Lua
  queue, one delivery per surviving participant. The physics event has no sender: Source is
  explicitly Unknown; Target and Other participant show the actual pair. No new physics events
  are generated by the inspector.
- `Timer.after` / `Timer.every`: actual timer firings delivered to the owner's `on_event`. Source
  identifies the timer owner; payload includes the timer ID. Scheduling/cancellation is unchanged.

The existing queue limits, delivery order, Lua failure handling, failed-instance suppression,
execution budget, timers and hot reload remain in place. This is not a second event bus.
Ordinary `on_update`, `on_fixed_update`, lifecycle calls, script load failures and arbitrary logs
are not represented as gameplay events. Their existing Console diagnostics remain available.

## Recorded data and limits

Rows have a monotonic sequence, Play session number, first-observed simulation time relative to Play, kind/name,
Source/Target snapshots (names, persistent scene identities if present, World/index/generation),
Other participant when available, script, handler name, actual handler start/end times, small
payload and result/error. Start/end times use the simulation clock, so synchronous calls normally
share a timestamp; these are not profiling durations.

Queued, Processing, Success, Error and Skipped are delivery statuses. Absent/failed handlers and
missing/dead targets are Skipped, with an explanation; they are not reported as successful calls.
If capture starts after enqueue, the first observed timestamp is delivery time, not an invented send time.
Only an actual function invocation records handler start. Lua error text is copied from existing
protected-call diagnostics; the original error logging and failed-script behavior are preserved.
A queued row may lack a final outcome if capture was interrupted before delivery. The details
explicitly report that delivery was not observed. Capture does not claim an unobserved result.

The deque holds 1024 rows by default, configurable from 128 to 8192, evicting the oldest first.
Payload is limited to 2048 bytes, error text to 4096, script keys to 1024, event names to 128,
entity names to 256 and persistent IDs to 128. There is no Lua table/object-graph serialization,
continuous disk logging, pointer to an Entity/World, or retained Lua reference. Disabled capture
skips snapshots/formatting and history lookups; status updates use constant-time deque indexing.
The UI clips the filtered row list rather than drawing the entire history.

## Filters and navigation

Case-insensitive event-name search, independent Source/Target name-or-ID filters, status and
Only errors operate on the stored history. `Selected as source/target` are explicit shortcuts:
selection does not automatically change filters. `Reset filters` restores all rows. Select a row
for payload, handler, timing, result and error. `Select in Hierarchy` uses the existing selection
API only if that exact World/index/generation is still alive. Destroyed objects and prior Play
sessions retain readable snapshots but cannot navigate to an unrelated/reused object.

No reliable correlation/parent event ID exists in these deferred queues. The panel therefore
shows chronological records, without inferring chains from neighboring timestamps.

## Lifetime

Stop Play retains copied history; the next Play gets a distinct session ID. Capture can continue
across sessions. Play Pause suspends normal Lua updates/timers as before. Hot Reload retains the
history, with each record's actual script/result. Project transition/close stops capture and clears
the history and filters. Buffer contents and settings are not saved in projects or scenes.

## Small demonstration

1. Open the existing `scenes/prefab_cabinet_demo.json` or instantiate `prefabs/cabinet.prefab.json`.
2. Create an Entity named Button. Add Lua Script `scripts/event_button.lua`, enable **Allow gameplay
   input**, and assign a cabinet DoorLeft or DoorRight to its `target` entity field.
3. Open Gameplay Events, Start Capture, and enter Play. Focus the Viewport and press **E**.
4. The button sends the existing `toggle` gameplay message; `cabinet_door.lua:on_event` opens/closes
   the actual door. Search `toggle`, inspect its Source/Target, and select its target in Hierarchy.
5. Stop Capture and Stop Play to inspect retained history. Start Play again for a new session.

For a controlled handler-error check, use an owned copy of the receiving script, replace the body
with `error("door jammed")`, and Hot Reload that copy. The event row reports Error with the same
Lua diagnostic as Console; restoring/reloading the script permits successful delivery again.
The regression fixture performs this without modifying shipped or user scripts.
